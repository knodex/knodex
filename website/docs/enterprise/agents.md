# Agent Audit Trail & Policy Validation

Knodex Enterprise extends the base [AI Agents](../user-guide/agents) feature with two capabilities: a durable PostgreSQL audit trail for all agent invocations, and automatic Gatekeeper policy validation for RGD Builder results.

## Agent Run Audit Trail

In the OSS edition, agent run records are stored in Redis with a 7-day TTL and a cap of 1 000 entries. Enterprise persists every invocation to the PostgreSQL `audit.events` table, subject to the same 90-day retention policy as all other audit events. Redis continues to serve the live run history UI; PostgreSQL provides the long-term compliance record. Hub agent runs (e.g., RGD Builder) are audited identically to BYOA runs — `agentType` is the agent CR name and `agentNamespace` is empty (the global-visibility convention).

### Audit Events

Three event types are emitted per run:

| Event | When | Key details |
|-------|------|-------------|
| `agent.invoked` | At invocation (202 returned) | `agentType`, `agentNamespace`, `actor`, `inputSummary`, `contextRef` |
| `agent.run.completed` | When A2A returns successfully | `runId`, `kagentSessionId`, `recommendationSummary`, `durationMs` |
| `agent.run.failed` | When A2A errors or times out | `runId`, `error`, `durationMs` |

Details are stored as JSONB in the `details` column. Field names listed in `enterprise.audit.redactFields` (Helm value) are stripped before storage.

### Querying Agent Audit Events

Use the Audit Trail page in the Knodex UI:

1. Navigate to **Settings → Audit Trail**.
2. Set the **Resource** filter to `agents`.
3. Use the **Action** filter to narrow to `agent.invoked`, `agent.run.completed`, or `agent.run.failed`.

Or query the API directly:

```bash
curl -H "Authorization: Bearer $TOKEN" \
  "$KNODEX_URL/api/v1/settings/audit/events?resource=agents&limit=50"
```

### Retention

Agent audit events follow the same retention schedule as all audit events (default: 90 days). Configure with:

```yaml
# values.yaml
enterprise:
  audit:
    retentionDays: 90  # or your organization's policy
```

## RGD Builder Policy Validation

When OPA Gatekeeper is installed in the cluster, Knodex Enterprise automatically validates every spec generated by the RGD Builder against your active Gatekeeper constraints before the result is shown to the user.

### How It Works

1. The RGD Builder agent returns a spec via the kagent A2A endpoint.
2. Knodex posts an `AdmissionReview` for each resource in the spec directly to the Gatekeeper validation webhook (`validation.gatekeeper.sh`).
3. The validation result is attached to the run record before the response is sent to the browser.

Validation never fails the run — if Gatekeeper is unreachable, the spec is returned with a `validation unavailable` warning instead of an error.

### Automatic Revision on Violation

If the initial spec fails validation, Knodex attempts one automatic revision:

1. The agent is re-invoked with the original requirement, the failing spec, and the list of violations.
2. The revised spec is validated once.
3. Both the original violations and the revision outcome are shown in the result panel.

There is no third attempt. If the revised spec still violates policies, both specs are shown alongside their respective violations so you can decide which to edit and use.

### Policy Validation Status

| Status | Shown when |
|--------|-----------|
| **Policy validated ✓** | All resources passed every active constraint |
| **Policy violations (N)** | One or more constraints flagged the spec; violations listed by constraint name and message |
| **Revised spec · Policy validated ✓** | Initial spec had violations; automatic revision passed |
| **Revised spec · Policy violations (N)** | Initial spec had violations; revision also has violations (both sets shown) |
| **Validation unavailable** | Gatekeeper webhook unreachable; spec returned without policy status |
| *(no badge)* | OSS build or no Enterprise license — validation not performed |

### Prerequisites

- Knodex Enterprise license with the `compliance` feature
- OPA Gatekeeper installed in the cluster with its `ValidatingWebhookConfiguration` active
- Knodex server `ServiceAccount` must be able to call the Gatekeeper webhook (standard cluster-admin or a custom `ClusterRole` granting access to `validation.gatekeeper.sh`)

Enable Gatekeeper integration in your Helm values:

```yaml
enterprise:
  gatekeeper:
    enabled: true
```

### Viewing Policy Violations

Each violation in the result panel shows:

| Field | Description |
|-------|-------------|
| **Constraint** | Name of the Gatekeeper `Constraint` that flagged the resource |
| **Kind** | The `ConstraintTemplate` kind (e.g., `K8sRequiredLabels`) |
| **Enforcement** | `deny`, `warn`, or `dryrun` |
| **Message** | Human-readable explanation from the Rego policy |
| **Resource** | The specific `spec.resources[].id` that triggered the violation |

For details on the underlying constraints, see [Compliance Management](compliance-management) and [Constraint Template Development](constraint-template-development).
